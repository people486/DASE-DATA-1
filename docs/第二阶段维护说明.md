# 第二阶段维护说明

## 第一阶段基线

核心结构为HTTP适配层、Service业务层、纯规则层、MongoDB存储层和静态前端。四个业务集合users sessions surveys responses必须保留其原有含义。第一阶段题目嵌入问卷，答卷引用survey_id与survey_revision。状态机draft到published到closed。已发布问卷不可改题。schema_version=1是文档结构版本；revision是草稿修订，不是数据库迁移版本。

docs/baseline-sha256.json记录核心源码和文档摘要；第二阶段先保存副本或提交Git，再修改。不要重新初始化一个系统覆盖第一阶段，更不能删除历史答卷以绕过迁移。

## 变更流程

1. 保存教师新需求原文，为每条需求列出已有行为、新行为和兼容影响。
2. 先运行阶段一17组回归测试并保存结果；备份lab4_survey数据库（如使用mongodump，由提交者配置工具及备份路径）。
3. 优先增加可选字段及默认值，在读取旧记录时兼容缺省；不要直接重命名或删除旧字段。
4. 修改现有logic或service模块，新增必要适配；保留API或显式引入版本接口，不能无说明改变原输入输出。
5. 数据变化使用独立迁移脚本：先dry-run统计影响，按schema_version筛选，更新后写新版本，重复执行不应重复修改。迁移前验证目标数据库名，勿对所有数据库批量操作。
6. 增加新需求测试和旧数据样本测试，再运行全部旧测试，记录失败原因与兼容处理。
7. 项目报告填写变更原因、字段前后对照、代码变化、迁移记录、兼容问题及测试证据。

## 可能的扩展位置

|若新需求为|保留并扩展位置|历史数据策略|
|---|---|---|
|新增题型或校验|logic题型分派、题目编辑器、统计分派|旧题type含义不变，新题用新type|
|更复杂条件组合|rules解释器增加明确的条件对象|旧op/value/target继续按旧语义解释|
|发布后修改问卷|新增survey_versions，responses保留revision引用|为当前已发布问卷生成快照，再允许新版本发布，不覆盖旧题|
|选项改名或重排|选项引入稳定ID，读写适配旧字符串|迁移时保存旧文本映射，历史统计依版本解析|
|大量答卷及新报表|statistics已有MongoDB聚合和分页，可按测量结果增加专用报表或索引|保留计数和平均口径，旧客户端按has_more读完values|
|协作作者|权限层扩展owner与members|owner_id继续有效，不把旧问卷暴露给所有账号|
|开放无登录匿名|单独设计匿名身份与限流防重策略|先修改需求解释和测试，不直接删除登录检查|

## 变更记录填写模板

每条记录包含：变更编号；教师原始需求；第一阶段已有设计；原设计不能满足之处；修改原因；涉及文件；集合及字段前后差异；schema_version变化；迁移命令与影响数量；API兼容情况；旧功能回归结果；新增测试结果；实际AI提示及人工修改；剩余问题。

未发布的新需求不提前写成已完成。若明确允许改变旧行为，应标注对应教师要求和受影响的旧测试，不能默默删除测试制造全绿。

按最终GitHub提交方式清理后，baseline-sha256.json更新为当前阶段一交付文件摘要；历史整理记录不随提交保留；版本变化以后以Git提交记录为准。后续修改前请先提交Git或保留本次基线。


## 本轮实现后的维护起点

23组自动测试全部通过；可视化编辑器仍输出原题目结构，schema_version为1，不需要迁移既有问卷。预览接口只读，不能转用正式responses接口。设置与题目一起按revision保存，新增字段需同时考虑草稿设置、预览快照和发布冻结。

统计values现为分页结果（默认20，上限100），浏览器每页10条。扩展导出功能时必须循环读取全部页，不能误把第一页当成全部答案；average是全部有效数字的平均值。按本轮baseline-sha256.json及Git提交记录继续维护，勿覆盖原MongoDB数据目录。
